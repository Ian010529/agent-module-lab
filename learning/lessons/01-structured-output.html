Lesson 01 — Structured Output + Schema Validation

项目落点：Creator Reply → structured extraction

状态：IN PROGRESS。目标不是记 API，而是能够独立设计第一版 Creator Reply extraction schema，并解释 validation 边界。

完成这一课后，你应该能做到

  • 解释 structured output 为什么比“prompt 里要求返回 JSON”更适合作为程序接口。
  • 用 Literal、可空字段和 nested model 表达业务事实，而不是制造 false precision。
  • 区分 schema validity、semantic correctness 和 deterministic business validation。
  • 追踪 reference 中 RouterSchema → with_structured_output → classification → routing → eval 的执行链。
  • 为 Creator Reply 设计一个最小但不丢关键业务关系的 schema。

Checkpoint A — 先预测，再看解释

Q1

RouterSchema 只允许 ignore / respond / notify。模型输出 classification="notify"，但标准答案其实应该是 respond。

Q2

同一个 RouterSchema 下，模型输出 classification="reply"。

Q3

达人报价 1800，campaign budget 是 1500。判断是否超预算应该主要交给谁？

核心模型

自然语言
   ↓
LLM semantic extraction
   ↓
structured object
   ↓
schema / type validation
   ↓
deterministic validation / business rules
   ↓
next workflow decision

Schema 可以保证“形状合法”，不能保证“模型读对了原文”。

例如原文是 £1200，模型错误抽成 £1500。只要字段类型和 Literal 合法，Pydantic 仍可能通过。因此后续还需要固定案例检查 extraction correctness。

Checkpoint B — 业务语义不能被 Schema 压扁

Creator Reply：

I'm definitely interested.

For one TikTok video my rate would be £1,200.
If you also want 3 months paid usage, it would be £1,600.

I could deliver by 20 October.

先不要看答案。请自己写出系统至少需要保留的业务事实，并思考为什么下面这个 schema 会丢信息：

class CreatorReply(BaseModel):
    interested: bool
    price_amount: float
    currency: str
    delivery_date: str
完成后再展开参考

关键问题不是“有两个数字”，而是两个价格分别绑定不同条件。仅保存 price_amount 会破坏“价格 ↔ 条件”的关系。

class Quote(BaseModel):
    amount: float
    currency: str | None
    condition: str

class CreatorReply(BaseModel):
    interest: Literal["interested", "not_interested", "conditional", "unclear"]
    quotes: list[Quote]
    can_deliver_by: str | None

这仍不是最终版本，只是展示 nested model 为什么出现。

Checkpoint C — Missing、Ambiguous、False Precision

Creator Reply：

Sounds interesting.
For TikTok I usually charge around 2–3k depending on usage.
I should be able to deliver sometime next month.
  1. 能否安全填一个精确的 price_amount？为什么？
  2. 如果没有货币符号或货币名称，currency 应该怎么表示？
  3. “sometime next month” 能否直接标准化成某个具体日期？
  4. 哪些判断需要 LLM，哪些可以由 code 在 extraction 后确定？
完成后再展开检查点
  • 2–3k 是 range，不应该捏造成 2500 这样的精确值。
  • 货币未给出时应保留 missing/None，而不是猜。
  • 模糊时间应保留原始语义，不能随意制造具体日期。
  • “文本是什么意思”属于 semantic extraction；字段是否缺失、数字比较、明确业务规则优先由 deterministic code 完成。
