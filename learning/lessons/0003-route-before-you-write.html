01 · 读两处源码，先预测

模型产出一个判断后，谁决定程序去哪？

打开 pinned email_assistant_hitl.py L54–99。只看下面这段摘录：

# result 来自 llm_router.invoke(...)
classification = result.classification
if classification == "respond":
    goto = "response_agent"
elif classification == "ignore":
    goto = END
elif classification == "notify":
    goto = "triage_interrupt_handler"
# 返回 Command(goto=goto, update=update)

预测：classification 已经是 respond。要确定下一个节点，还要再问一次 LLM 吗？

接着看 L160–177 的 llm_call：模型用上下文生成内容与调用请求。这和上一段确定 goto 的职责不同。

迁移时只带走边界：如果业务规则已经明确“缺币种就先澄清”，应用可执行这条已批准的规则，LLM 可以负责把澄清写成自然语言。本项目尚未决定各状态的最终 action 映射；不能仅凭一个 status 就提前替 Own Design 下结论。

口头练习：把这两段分别说成一句“输入 → 处理 → 输出”。不要只说“都由 AI 处理”。

02 · 输入追踪

一句看似自然的回复，究竟凭什么写出来？

在 llm_call，response agent 的输入是：

system message:
  agent_system_prompt_hitl.format(
    tools_prompt=HITL_TOOLS_PROMPT,
    background=default_background,
    response_preferences=default_response_preferences,
    cal_preferences=default_cal_preferences
  )
+ state["messages"]

L65–75 把原邮件放进 messages；后面 Tool observation、人类反馈也会加入 messages。prompts.py L74–109 则定义如何使用这些信息，缺少直接问题的答案时先通过 Question 询问用户。

找来源：原邮件没有给出寄样日期，但 response preferences 要求“简洁专业”。这是否足够支持“我们周五寄出样品”？

参考实现也有适用范围。default_response_preferences 对活动邀请写了“不承诺”，但对约会场景又允许确认时间。它不是全局 no-commit 安全策略，不能直接照搬成 Creator Outreach 的权限规则。

本项目更严格的“不自动接受报价、承诺寄样、修改预算或发送真实商务邮件”来自 project-scope.md。Prompt 能表达约束，但不能替代应用的权限边界，也不能保证每句生成文本都真实。

03 · 调用请求 → 执行边界

“写了草稿”和“执行发送”隔着哪一行？

先看 默认 write_email 的完整函数体：

@tool
def write_email(to: str, subject: str, content: str) -> str:
    """Write and send an email."""
    # Placeholder response - in real app would send email
    return f"Email sent to {to} with subject '{subject}' and content: {content}"
必须分清契约与实现：这个 Tool 代表“写并发送”的动作契约，但 pinned 默认实现是 mock / placeholder，只返回字符串，没有调用邮件服务。不能把 “Email sent…” 当成真实投递证据。若接入真实发送，外部副作用发生在执行发送实现时；仅产生 content 或 tool_calls 都还不是发送。

HITL 拦截的具体位置在 interrupt_handler L188–255：

# tool_call 已经由模型产生
hitl_tools = ["write_email", "schedule_meeting", "Question"]
# write_email 在名单内，因此先构造 request，暂停等待：
response = interrupt([request])[0]

if response["type"] == "accept":
    tool = tools_by_name[tool_call["name"]]
    observation = tool.invoke(tool_call["args"])

HITL 审查的是已生成的动作与参数，在执行之前。这个节点也会拦截 Question，因此“所有 interrupt 都是发送审批”同样不准确。不在 hitl_tools 里的动作会走直接执行路径。

核对实际分支：accept / edit L250–287；ignore / response L303–346。

反事实：如果把真实发送放到 interrupt 之前，再让人点 ignore，会怎样？

只补一条恢复语义，避免错误理解

官方 interrupt 文档说明暂停/恢复需要 checkpointer 与 thread ID；恢复时包含 interrupt 的节点会从头重新执行，所以 interrupt 之前的副作用要考虑重复执行。这不是“暂停 Python 栈后从下一行继续”的通用保证。本课只理解风险位置，不提前设计持久化、幂等或重试系统。

04 · 迁移练习，不做 Own Design

有依据的草稿，也要守住授权边界。

练习事实：CreatorReply 中一份当前报价为 800，currency = None；PolicyDecision 给出 missing_information，reason 包含 missing_quote_currency。没有其他获批业务事实或合作承诺。

逐句审查：下面哪句可以作为“澄清币种”的草稿候选？这里只审内容，不决定最终状态映射。

再换一个条件：若 PolicyDecision = within_policy，是否就能写“我们接受报价，合作确认”？

项目依据：evaluate_policy 的既有职责与 默认权限边界。

错误应该落在哪层？状态与动作不符，检查 control flow；加入未知事实，检查上下文和生成结果；尝试未经批准的外部写操作，检查执行权限。把三类失败全部归为“prompt 再写好一点”，会丢掉真正的边界。
