Lesson 0002 · Campaign Context + Policy Gate

Read the tool loop
before you design it.

这一课不是先告诉你“Campaign lookup 应该怎么做”。先把 pinned agents-from-scratch 里的 Tool Calling 技术链真正追一遍：Tool 如何定义、如何暴露给模型、模型返回什么、程序如何执行、结果如何回到模型，以及哪里其实根本没有 Agent 决策。

约 20–25 分钟 Source-first 目标：学完即可进入 Own Design

Reference 1 · Tool definition

第一步：Tool 先是普通 Python 能力，再被包装成模型可调用接口。

先看 pinned reference 的 tools/default/email_tools.py：

@tool
def write_email(to: str, subject: str, content: str) -> str:
    """Write and send an email."""
    return ...

@tool
class Question(BaseModel):
    """Question to ask user."""
    content: str

这里有三个东西值得分开：

东西作用
Python function / class真正的应用能力或参数模型。
@tool把 callable / schema 暴露成 LangChain Tool 接口。
函数签名、类型、docstring形成模型可看到的 tool name / description / argument schema。
关键点：Tool 不是 LLM 里的函数。真正的函数仍然运行在你的 application runtime；模型拿到的是“我有哪些动作、参数长什么样”的接口描述。
Reference 2 · Exposure boundary

第二步：不是定义了 Tool，模型就自动拥有它。

tools/base.py 先建立应用可用的 tool 集合：

all_tools = {
    "write_email": write_email,
    "Done": Done,
    "Question": Question,
    "schedule_meeting": schedule_meeting,
    "check_calendar_availability": check_calendar_availability,
}

然后 get_tools(...) 决定这一条 workflow 实际暴露哪些：

tools = get_tools([
    "write_email",
    "schedule_meeting",
    "check_calendar_availability",
    "Question",
    "Done",
])

同时 reference 建了一个 dispatch map：

tools_by_name = get_tools_by_name(tools)

# 得到类似：
{
    "write_email": <tool>,
    "schedule_meeting": <tool>,
    ...
}

这一步不是 LLM 做的，而是应用代码先决定模型的 action surface。这也是最小权限的技术落点之一：模型只能选择你真正绑定给它的动作。

Reference 3 · bind_tools

第三步：把 Tool schema 交给模型，但仍然没有执行任何 Tool。

llm_with_tools = llm.bind_tools(
    tools,
    tool_choice="required"
)

当前 LangChain reference 中，bind_tools 接受 callable / Pydantic class / BaseTool 等 tool definitions，并返回一个仍然需要被 invoke 的 runnable。tool_choice="required" 的含义是：模型必须产生至少一个 tool call；它不是“现在立刻执行某个 Python 函数”。

在 reference 的 llm_call 中，真正调用模型的是：

llm_with_tools.invoke(
    [system_message] + state["messages"]
)

返回值会被放进 state["messages"]。如果模型决定采取动作，这个 AI message 会带有 tool_calls。

Reference 4 · What the model actually returns

模型不执行函数，它返回一个结构化“调用请求”。

reference 后面的代码直接访问：

for tool_call in state["messages"][-1].tool_calls:
    tool_call["name"]
    tool_call["args"]
    tool_call["id"]

所以在这一版 reference 里，我们至少可以确定一个 tool call 有三个关键字段：

字段谁产生谁消费
nameLLMapplication 用来选择真正的 Tool
argsLLM传给 tool.invoke(...)
idtool-calling protocol把后续 observation 对回这次调用
 
AIMessage
└── tool_calls
    └── {
          "name": "...",
          "args": {...},
          "id": "..."
        }
Reference 5 · Runtime dispatch

真正执行 Tool 的是 application，不是模型。

非 HITL 版本的 tool_node 很直接：

for tool_call in state["messages"][-1].tool_calls:
    tool = tools_by_name[tool_call["name"]]
    observation = tool.invoke(tool_call["args"])

    result.append({
        "role": "tool",
        "content": observation,
        "tool_call_id": tool_call["id"],
    })

逐行拆开：

  1. 从最新 AI message 读取模型提出的调用。
  2. 用 name 在应用自己的 tools_by_name 中找到真正 Tool。
  3. 用模型生成的 args 调 invoke。
  4. 拿到真实执行结果 observation。
  5. 构造一个 role="tool" 的 message，用同一个 tool_call_id 对回原请求。
  6. graph 再回到 llm_call，模型才能看到执行结果并决定下一步。
LLM proposes action
      ↓
application executes action
      ↓
observation becomes message
      ↓
LLM reasons again
Reference 6 · HITL changes execution, not the basic protocol

HITL 版本只是把某些 Tool 的执行前插入人工控制。

email_assistant_hitl.py 先定义：

hitl_tools = [
    "write_email",
    "schedule_meeting",
    "Question",
]

不在名单里的 Tool 直接执行：

if tool_call["name"] not in hitl_tools:
    tool = tools_by_name[tool_call["name"]]
    observation = tool.invoke(tool_call["args"])
    ...
    continue

在名单里的才进入 interrupt(...)，然后根据 human 的 accept / edit / ignore / response 决定是否执行或修改参数。

现在先不要展开 HITL。当前 Slice 只需要看懂：Tool call 已经由模型产生；HITL 是 application 在“是否真正执行这个动作”这一层再加控制。
Reference 7 · Agent loop

为什么它叫 loop：Tool observation 还会回给模型。

非 HITL 版本的 graph 是：

START
  ↓
llm_call
  ↓
should_continue
  ├── Done → END
  └── Action → environment/tool_node
                     ↓
                  llm_call
                     ↓
                    ...

Done 本身也被包装成 Tool。reference 用它作为模型发出的 termination signal；其他 Tool call 则进入执行节点，然后重新回到 LLM。

这就是你之前学过的 Agent Loop 在代码里的具体形态：

LLM → action → observation → LLM → ... → stop
Contrast · Not everything is a Tool decision

同一个 reference 里，也有完全不同的 deterministic control。

Triage 的分类虽然由 LLM 产生，但分类一旦得到，代码直接处理：

classification = result.classification

if classification == "respond":
    goto = "response_agent"
elif classification == "ignore":
    goto = END
elif classification == "notify":
    goto = "triage_interrupt_handler"

这里没有：

bind_tools(...)
→ LLM 决定调用哪个 route tool
→ tool.invoke(...)

因为应用已经有一个明确的 mapping：

classification → next node

所以 reference 自己已经同时展示了两种控制权：

控制权Reference 里的形态
需要模型根据语义选择动作bind_tools → tool_calls → invoke
结果已知后按明确规则继续if / elif → Command(goto=...)
Technical foundation · Bring it back to context

Business data、runtime context、Tool 是三个不同概念。

Slice 2 会接触 Campaign 数据。先只建立这个最小模型：

business system
  └── Campaign record / policy
           ↓  lookup
runtime context for this decision
           ↓
policy evaluation

Business data 是系统里本来存在的数据；context 是当前这次决策真正拿进来的那部分信息；Tool 则只是“是否把某个能力交给模型自主选择”的接口形式。

因此，一个普通 Python function 完全可以内部调用 DB / HTTP API；“访问外部系统”本身不等于“必须让 LLM Tool Calling”。

当前 Slice 只需要掌握一个 context 原则：下游只需要什么，就让 lookup boundary 返回什么；不要因为源系统有一整个 Campaign object，就把整个对象都塞进后续上下文。具体字段留到 Own Design 再由你决定。

Technical foundation · Policy gate

Policy Gate 的技术角色：对已经结构化的事实做确定性判断。

Slice 1 已经把自然语言变成 CreatorReply。Slice 2 会再取得 Campaign Policy。只要某条规则可以写成明确程序条件，它就不需要 LLM 再“理解”一次：

reply fact + policy fact
          ↓
 deterministic comparison
          ↓
 decision + reason

例如数值阈值、明确允许的币种集合、必填信息是否缺失，都天然适合普通代码。语义仍然模糊的东西则不能假装成确定性 rule；具体边界会在 Own Design 时逐项判断。

Practice · Read the source, not the slogan

先检查你有没有真正读懂调用链。

1. 哪一步只是让模型“知道有哪些 Tool”，并没有执行 Python Tool？

2. reference 里真正调用 Python Tool 的是谁？

3. tool_call_id 在这条链里最直接的作用是什么？

4. get_tools([...]) 在 reference 中最重要的架构意义是什么？

Final gate

通过这 5 题，才进入 Own Design。

1. AIMessage.tool_calls 更接近什么？

2. 模型返回 {"name": "check_calendar_availability", "args": {"day": "Friday"}} 后，真正执行外部能力的关键一步是？

3. Triage 得到 classification="respond" 后，reference 为什么不用 Tool Calling 再决定去哪？

4. 一个函数内部会访问 HTTP API。是否因此必须包装成 Agent Tool？

5. 已有结构化 quote=1800 和 policy max_budget=1500，第一层判断应该交给？

Transfer · This decides whether you can Own Design

不要回看上面的答案，用自己的话回答。

A. 从 @tool 开始，到 Tool 执行结果重新回到 LLM 为止，完整讲一遍 reference 的调用链。至少说出：

@tool
get_tools
bind_tools
AIMessage.tool_calls
name / args / id
tools_by_name
invoke
role="tool" + tool_call_id
back to llm_call

B. 现在把场景换成我们的 Slice 2：输入已经有 CreatorReply + campaign_id，每次都必须取得这个 campaign 的规则。你会保留上面 Tool Loop 的哪些部分、删掉哪些部分？为什么？

C. Campaign Policy 被取回来以后，哪些类型的判断你会放进 deterministic policy gate？什么类型的判断你不会硬塞进去？

这三个回答才是真正的 learning gate。通过后我们不再继续上课，直接进入 Own Design。

Boundary

这一课刻意没有展开这些内容。

RAG、Memory、MCP、动态 Tool Registry、Multi-Agent、Redis、Queue，以及 HITL 的持久化机制都不属于当前 learning gate。它们只有被后续实际 Slice 需求触发时才学。

Takeaway

不是背一句“普通函数 vs Tool”，而是掌握控制权在哪里。

Tool definition
    ↓
model can propose an action
    ↓
application decides what is exposed
    ↓
application executes the action
    ↓
observation returns to the model

vs.

known next step
    ↓
application executes it directly
