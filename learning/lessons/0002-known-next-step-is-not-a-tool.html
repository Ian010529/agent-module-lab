Lesson 0002 · Campaign Context + Policy Gate

A known next step
is not an Agent Tool.

这一课只解决一个边界：当程序已经知道下一步必须根据 campaign_id 查询 Campaign Policy 时，为什么应该直接调用普通函数 / API，而不是把查询暴露给 LLM 再让它决定。

约 10–15 分钟 Slice 2 technical foundation 需要：已完成 Reply Extraction
Why this matters

“访问外部数据”不等于“必须做成 Tool”。

Tool calling 的价值在于：模型面对多个可能动作时，可以根据当前语义决定是否调用、调用哪个、参数是什么。OpenAI 的 function calling 文档也把 tool calling 描述为让模型访问应用功能与外部数据，并说明默认情况下模型会决定何时、如何调用工具；tool_choice 可以进一步约束这种选择。[5]

但 Slice 2 已经有两个确定事实：

input = CreatorReply + campaign_id

下一步固定：
campaign_id
   ↓
lookup campaign policy
   ↓
deterministic policy checks
关键判断：
如果“下一步是什么”和“查询 key 从哪里来”都已经由 workflow 确定，就没有必要再付出一次 LLM 决策成本，让模型重新决定同一件事。
Two different responsibilities

普通函数负责执行已知步骤；Agent Tool 承担模型决策空间。

Direct lookup / 普通函数

程序已经知道要查 Campaign Policy，并且已有可信的 campaign_id。代码直接调用接口。

Agent Tool

模型需要根据语义，在多个可选动作之间决定下一步，例如查日历、提问、写邮件。

Deterministic policy code

事实和政策都已拿到后，预算、币种、允许范围等明确规则由代码判断。

# Slice 2 的目标形态

policy = get_campaign_policy(campaign_id)
decision = evaluate_policy(reply, policy)

这里的 get_campaign_policy 完全可以在内部访问数据库或 HTTP API。它不是 Agent Tool，并不意味着它只能是“本地小函数”；区别在于谁决定调用它。

Reference implementation

在 pinned 源码里，Tool 是被刻意放进模型的动作空间。

参考项目先由代码选择允许暴露的工具：

tools = get_tools([
  "write_email",
  "schedule_meeting",
  "check_calendar_availability",
  "Question",
  "Done",
])

get_tools 本身只是普通 Python 代码：从一个已知工具集合里取出指定工具。[1] 然后这些工具被绑定到 LLM：

llm_with_tools = llm.bind_tools(
    tools,
    tool_choice="required"
)

LangChain 的 API reference 明确说明：bind_tools 把工具定义绑定给模型，而 tool_choice 控制模型的工具选择行为；"required" / "any" 会要求至少调用一个工具。[4]

随后，参考项目读取模型产生的 tool_calls，根据名字找到对应工具并执行。HITL 版本甚至先判断该工具是否需要人工审批，再执行。[2]

这说明 Tool 在这里不是“任何外部函数的包装名”，而是模型可选择的 action interface。

Contrast

同一份参考代码也展示了 deterministic routing。

在 triage 阶段，模型只负责产生结构化分类。分类一旦得到，后面的控制流不是再让 Agent 选择，而是普通 if / elif：

if classification == "respond":
    goto = "response_agent"
elif classification == "ignore":
    goto = END
elif classification == "notify":
    goto = "triage_interrupt_handler"

也就是：模型负责它真正擅长且必要的语义判断；一旦结果已经明确，程序用确定性控制流继续。[3]

Slice 2 要沿用的是这个边界，而不是机械复制参考项目的 Tool 结构。

Failure surface

把固定 lookup 做成 Tool，会额外引入什么？

假设每次处理 Creator Reply 都必须读取同一个 campaign_id 的 policy。若仍让 LLM 调 Tool，就多出原本不存在的失败路径：

本来：
campaign_id → lookup(policy)

Tool 化以后：
campaign_id
  → LLM 是否想起要查？
  → 选对 tool 吗？
  → 参数 campaign_id 填对吗？
  → tool call 是否符合 schema？
  → lookup(policy)

这些额外步骤只有在模型确实需要选择动作时才值得承担。当前 Slice 没有这个需求。

最小权限也更清楚：
Campaign lookup 只返回 policy gate 真正需要的字段，而不是把整个 Campaign 对象、所有业务接口或一组无关 tools 暴露给模型。
Practice

判断“谁应该拥有这个决定”。

Case 1. 输入已经带有可信 campaign_id，每条回复在 policy gate 前都必须查询对应 campaign 的预算和币种。应该怎样调用？

Case 2. 回复 Agent 需要根据邮件内容自己决定：查日历、向用户追问，还是直接写邮件。这里更适合？

Case 3. 已得到 quote=1800、max_budget=1500。第一步判断是否超预算应该交给？

Final gate

最后四题：通过后才进入 Own Design。

不要背“Tool 不好”。判断标准是：当前步骤是否真的需要模型拥有选择权。

1. campaign_id 已知，下一步 100% 是获取该 campaign 的 policy。选择？

2. 模型需要自行判断是 check_calendar、Question 还是 write_email。选择？

3. “只要函数访问数据库或 HTTP API，就应该包装成 Agent Tool。”对吗？

4. Campaign Policy 明确规定 currency=USD、max_budget=1500，Creator Reply 是 1800 EUR。第一层 policy 判断应该是？

Transfer question

回到我们的项目，不看答案说清楚这条链。

CreatorReply + campaign_id
          ↓
         ???
          ↓
 Campaign Policy
          ↓
         ???

within_policy / missing_information / human_review

在 ChatGPT 里用自己的话回答两点：

  1. 两个 ??? 分别应该是什么？
  2. 什么条件变化后，你才会重新考虑把 Campaign 查询暴露成 Agent Tool？

这两题用于真正的 learning gate。HTML 里的选择题全部正确，还不等于已经形成可迁移的设计判断。

Takeaway

只记这一句。

Known workflow step → direct code / API
Semantic action choice → controlled Agent Tool
Known business rule → deterministic code
